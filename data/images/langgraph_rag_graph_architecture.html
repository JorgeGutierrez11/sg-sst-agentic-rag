Consulta normativa SG-SST: del turno conversacional a la respuesta fundamentada

Este diagrama muestra cómo el grafo creado por build_langgraph_rag recibe una consulta, busca información normativa y entrega una respuesta. Los paneles dividen el recorrido para explicar con claridad qué ocurre en cada etapa.

01 · PREPARACIÓN

Perfil, memoria conversacional y recuperación R3

Qué ocurrePrimero se actualiza el perfil y se recupera la memoria asociada al thread_id para formar business_context.current_context. Luego R3 conserva la pregunta original, reúne y ordena los resultados, y reemplaza los fragmentos por sus documentos padre antes de revisar la evidencia.
02 · DECISIÓN

Instrumentación, grading y bifurcación exacta de evidencia

Cómo decideevidence_route toma la ruta with_evidence cuando state.get("documents") tiene contenido; si está vacío, toma without_evidence. El grafo actual no aplica una revisión adicional de suficiencia ni Self-Refine.
03 · CIERRE

Actualización de memorias, resultado público y finalización

Cierre comúnTanto la respuesta generada como el fallback siguen el mismo cierre: actualizan el historial en business_context, guardan el turno en la memoria semántica, construyen LangChainRagResult y llegan a END. El API usa conversation_id como thread_id, mientras el CLI crea uno por sesión.
04 · BOUNDARIES

Dependencias externas y ensamblaje del runtime

Preparaciónbuild_runtime abre los índices existentes, carga el reranker y los documentos padre, crea InMemorySaver e InMemoryStore, y prepara el grafo para responder. No crea ni actualiza Chroma o BM25; durante la ejecución solo escribe en el estado y en la memoria temporal de la conversación.
STATE · I/O

Contrato global alcanzable de RagGraphState

Entrada y clave de ejecución

Invocación del turno

Cada turno comienza con graph.invoke({"question": question}, {"configurable": {"thread_id": id}}). El API identifica la conversación con conversation_id; el CLI conserva un UUID durante la sesión.
